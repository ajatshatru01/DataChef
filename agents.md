## 1. Agent Role and Identity

DataChef contains a single agent: **the Investigation Agent**. It is not a general-purpose assistant. It is a domain-specific investigator whose only job is to understand a structured dataset, formulate analytical questions, execute appropriate analytical tools, evaluate the computed evidence, and communicate justified conclusions.

**The agent is explicitly not:**
- A chatbot that answers from its parametric knowledge.
- A code generator that produces Python or SQL for the user to run.
- A dashboard tool that produces visualizations on demand.
- A source of numerical truth. Every number it cites must come from the analytical engine.

**The agent is:**
- An orchestrator that selects the right tool for each analytical step.
- An interpreter that reads tool outputs and decides what they imply.
- A planner that determines whether more evidence is needed before concluding.
- A communicator that explains its reasoning and distinguishes fact from inference.

This role definition is enforced in the system prompt and reinforced by the closed tool set. The agent cannot bypass it by generating code.

---

## 2. Agent Modes

The Investigation Agent operates in two modes depending on how it is invoked:

### 2.1 Conversational Mode

Triggered by a user submitting a natural-language question from the chat interface.

The agent receives the question, the dataset context, and the conversation history. It investigates the question using the available tools, accumulates evidence over multiple turns if necessary, and returns a structured `Finding` to the UI.

**Examples of questions this mode handles:**
- "Which columns have the most missing values?"
- "Compare average sales across regions."
- "Is there a trend in monthly revenue?"
- "What are the most unusual rows in the dataset?"
- "Are product category and customer segment related?"

### 2.2 Discovery Mode

Triggered when the user initiates autonomous discovery.

The agent does not receive a specific question. Instead, it receives a ranked list of candidate findings generated by the `DiscoveryEngine`. It prioritizes these candidates, selects a subset to investigate (up to a configurable maximum), and runs each one through the standard iterative investigation loop.

The result is a structured discovery report containing multiple findings, each with supporting evidence.

## 3. InvestigationAgent — Core Design

**Module:** `datachef/agent/investigation_agent.py`

### 3.1 State Machine

The agent operates as a simple state machine within each investigation:

```
IDLE
  │
  │  receive(question or candidate)
  ▼
PLANNING
  │
  │  build context + send to model
  ▼
AWAITING_RESPONSE
  │
  ├── model returns text ──────────────────► COMPOSING
  │
  └── model returns tool call
        │
        ▼
      VALIDATING
        │
        ├── invalid ────────────────────────► AWAITING_RESPONSE  (error fed back)
        │
        └── valid
              │
              ▼
            EXECUTING
              │
              ▼
            EVALUATING
              │
              ├── limits not reached ─────► PLANNING  (loop continues)
              │
              └── limits reached ─────────► COMPOSING  (forced conclusion)

COMPOSING
  │
  │  build Finding from accumulated evidence
  ▼
DONE
```

State transitions are driven by the model's response and the current loop counters. There are no external interrupts or concurrent state changes during a single investigation.

### 3.2 Bounded Loop Guarantees

Every investigation has hard upper bounds. These are checked at the `EVALUATING` state and enforced regardless of model output:

| Parameter | Environment Variable | Default |
|---|---|---|
| Maximum tool calls per investigation | `DATACHEF_MAX_TOOL_CALLS` | 10 |
| Maximum turns (model round-trips) | `DATACHEF_MAX_TURNS` | 8 |
| Maximum wall-clock time (seconds) | `DATACHEF_MAX_WALL_SECONDS` | 120 |
| Maximum tokens per tool result | `DATACHEF_MAX_RESULT_TOKENS` | 2000 |
| Maximum candidates in discovery mode | `DATACHEF_MAX_DISCOVERY_CANDIDATES` | 6 |

When any limit is reached, the agent transitions to `COMPOSING` with a note that the conclusion was reached under the applicable limit. This note is surfaced in the final finding.

### 3.3 Entry Points

```python
class InvestigationAgent:

    def investigate(self, user_message: str) -> Finding:
        """
        Handle a single conversational question.
        Runs the bounded investigation loop and returns a structured Finding.
        """

    def discover(self) -> List[Finding]:
        """
        Run autonomous discovery.
        Generates candidates via DiscoveryEngine, prioritizes with the model,
        and investigates the top N, returning one Finding per candidate.
        """
```

Both methods are synchronous in the initial release. Async versions may be added in a later iteration to support live progress streaming to the Streamlit UI.

## 4. Prompt Design

### 4.1 System Prompt Structure

The system prompt is constructed once per session by `PromptBuilder` and reused across all turns. It is structured as sequential sections:

```
SECTION 1 — Role and Operating Principles
  Your identity, investigative mandate, and the non-negotiable rules
  you must follow in every response.

SECTION 2 — Dataset Schema
  Column names, inferred roles (numeric / categorical / datetime / text / id),
  data types, row count, and column count.
  This is the complete list of valid column names for tool arguments.

SECTION 3 — Dataset Profile Summary
  Concise statistics: null percentages, cardinality, top values for
  categoricals, basic descriptive stats for numerics.
  No raw rows are included.

SECTION 4 — Tool Registry
  Full JSON schemas for all available tools.
  Each tool entry includes its name, description, parameter schema,
  and a brief usage example.

SECTION 5 — Investigation Rules
  Explicit behavioral constraints:
  - Always use a tool before citing a number.
  - Do not invent column names or values.
  - Conclude when evidence is sufficient; do not over-investigate.
  - Distinguish between computed facts and interpretations.
  - Acknowledge limitations and uncertainty where present.
  - Do not claim causation from correlation.
```

The system prompt is deterministic for a given dataset profile and tool registry. It does not change between turns.

### 4.2 Per-Turn Context

Each turn, `ContextBuilder` appends a structured user-role message containing:

1. **Current objective:** The original question or discovery candidate being investigated.
2. **Accumulated evidence:** Condensed summaries of tool results collected so far in this investigation (last 3 by default, configurable).
3. **Turn instruction:** A concise directive appropriate to the current state — e.g., "Continue investigating. You have used N of M allowed tool calls." or "This is your final turn. Please provide your conclusion."

The turn instruction becomes progressively more directive as limits approach, nudging the model toward a conclusion rather than additional tool calls.

### 4.3 Prompt Engineering Principles

These principles guide all prompt changes and are treated as invariants:

**Ground truth from tools.** The system prompt explicitly prohibits the model from citing numbers it has not obtained from a tool call. If the model produces a numerical claim without a corresponding tool call record, it is flagged as a hallucination in the finding.

**Closed vocabulary for columns.** The system prompt lists every valid column name. The validator rejects tool calls referencing columns that do not exist. This prevents the model from inventing plausible-sounding column names.

**Explicit uncertainty language.** The model is instructed to use hedged language ("the data suggests", "this may indicate") for interpretations and direct language ("the computed mean is") for tool outputs.

**No over-investigation.** The model is instructed to conclude as soon as it has sufficient evidence to answer the question. Unnecessary tool calls increase cost and latency without improving findings.

**Temperature.** All inference requests use a low temperature (default: 0.2) to promote deterministic, consistent tool selection and structured output. This is configurable but should remain low for tool-calling tasks.

## 5. Tool Calling

### 5.1 Tool Call Lifecycle

```
Model produces tool call response
        │
        ▼
[ToolCallParser]
  - Extract tool name and arguments from response
  - Handle strict JSON format and markdown fallback
  - Reject malformed structures immediately
        │
        ▼
[ToolValidator]
  - Verify tool name exists in registry
  - Verify all required parameters are present
  - Verify column names exist in the dataset
  - Verify enum values match allowed options
  - Verify numeric values are within allowed ranges
        │
        ├── INVALID ──► construct error message ──► feed back to model as tool result
        │
        └── VALID
                │
                ▼
        [ToolRegistry.dispatch(tool_name, validated_args)]
                │
                ▼
        [Analytical function executes]
                │
                ▼
        ToolResult
          ├── tool_name: str
          ├── arguments: dict
          ├── result: dict | list | scalar
          ├── chart_json: str | None
          ├── execution_time_ms: int
          └── truncated: bool
                │
                ▼
        [Token cap applied: result summarized if too long]
                │
                ▼
        [Appended to InvestigationState.tool_call_log]
                │
                ▼
        [Serialized result fed back to model as tool message]
```

### 5.2 Tool Call Record Format

Every tool call is stored as a `ToolCallRecord` in `InvestigationState.tool_call_log`:

```
ToolCallRecord
├── call_id: str              # unique ID for this call
├── turn_index: int           # which model turn produced this call
├── tool_name: str
├── arguments: dict           # validated arguments (as submitted)
├── result_summary: str       # human-readable summary of result
├── result_data: dict         # structured result (serializable)
├── chart_json: str | None    # serialized Plotly figure
├── execution_time_ms: int
├── validation_passed: bool
├── execution_succeeded: bool
├── result_truncated: bool
├── error_message: str | None # populated only if validation failed
└── timestamp: datetime
```

This record is later included verbatim in the `InvestigationRecord` for reproducibility.

### 5.3 Error Handling and Feedback

When a tool call fails validation, the error is formatted as a tool result and returned to the model:

```json
{
  "role": "tool",
  "tool_call_id": "<id>",
  "content": "ERROR: Tool call rejected. Reason: Column 'revnue' does not exist in the dataset. Valid column names are: ['revenue', 'region', 'category', 'quantity']. Please correct your tool call."
}
```

The model receives this as context for its next response. This allows it to self-correct without external intervention. Validation errors count toward the turn limit but not the tool-call limit (since no tool was executed).

## 6. Discovery Agent Behaviour

### 6.1 Candidate Generation

When the user initiates discovery mode, `DiscoveryEngine` runs a predefined suite of checks against the `DatasetProfile` without making any API call:

| Check | Produces | Scoring Factor |
|---|---|---|
| Outlier scan | Columns with candidate outliers | IQR fence violation rate |
| Group difference scan | (numeric col, categorical col) pairs with large group differences | Effect size (Cohen's d) |
| Correlation scan | Strongly correlated variable pairs | Absolute Pearson coefficient |
| Trend scan | Time-indexed columns with monotonic trends | Spearman rho magnitude |
| Missingness scan | Columns with notable null rates | Null percentage |
| Duplicate scan | Duplicate row presence | Duplicate fraction |
| Cardinality scan | Categoricals with unexpected high or low cardinality | Deviation from expected range |

Each check produces zero or more `CandidateFinding` objects:

```
CandidateFinding
├── check_type: str
├── description: str           # human-readable description of the candidate
├── involved_columns: List[str]
├── heuristic_score: float     # 0.0 – 1.0 (higher = more likely interesting)
├── suggested_tools: List[str] # tools that should be used to investigate
└── context_data: dict         # pre-computed statistics that motivated the candidate
```

The full list is ranked by `heuristic_score` descending and passed to the agent.

### 6.2 Prioritization Prompt

The agent receives the ranked candidate list and sends a single prioritization request to the model:

**System prompt:** Standard session system prompt (schema, profile, tools).

**User message structure:**
```
You are running autonomous discovery on this dataset.
The following candidate findings have been identified by the analysis engine,
ranked by a heuristic score. Your task is to select the most promising
candidates to investigate in depth.

Select up to {MAX_CANDIDATES} candidates. Order them from most to least interesting.
Return your selection as a JSON array of candidate indices.

Candidates:
[0] {candidate_0.description} (score: {score:.2f})
[1] {candidate_1.description} (score: {score:.2f})
...

Return only the JSON array. Example: [2, 0, 4]
```

The model's response is parsed with `ToolCallParser` (JSON extraction mode). If it is malformed, the top N candidates by heuristic score are used as a fallback.

### 6.3 Per-Candidate Investigation

Each selected candidate is investigated using the standard `investigate()` loop with the candidate's `description` as the question and its `suggested_tools` provided as hints in the per-turn context.

The agent is not required to follow the suggested tools. They are hints that reduce the number of exploratory turns needed.

## 7. Finding Composition

### 7.1 Finding Data Model

A `Finding` is the output of a single investigation. It is composed by `FindingComposer` from the `InvestigationState` at the end of the loop.

```
Finding
├── finding_id: str
├── session_id: str
├── trigger: Literal["conversational", "discovery"]
├── question: str                      # original user question or candidate description
├── conclusion: str                    # model's final natural-language conclusion
├── evidence: List[Evidence]
│   ├── tool_name: str
│   ├── arguments: dict
│   ├── result_summary: str
│   ├── chart_json: str | None
│   └── is_primary: bool               # True for the most decisive evidence
├── interpretation: str                # model's interpretation of the evidence
├── limitations: List[str]             # stated caveats and limitations
├── unverified_numerical_claims: List[str]
├── tool_call_log: List[ToolCallRecord] # includes rejected and failed calls
├── tool_call_count: int
├── turn_count: int
├── hit_limit: bool                    # True if loop was terminated by a limit
├── model_id: str
├── provider: str
├── temperature: float
└── created_at: datetime
```

### 7.2 Separation of Evidence and Interpretation

A `Finding` deliberately separates three things:

1. **Evidence** — the tool name, the validated arguments, and the result. This is objective and reproducible. Any user can re-run the tool with the same arguments and get the same result.

2. **Interpretation** — the model's reading of what the evidence implies. This is subjective and may be incorrect. It is displayed with a clear label distinguishing it from the evidence.

3. **Limitations** — what the evidence does not show, what confounders are not addressed, what additional investigation would be needed. These are extracted from the model's final response.

The UI renders all three sections separately in the `FindingCard` component so users can engage critically with the conclusions.

## 8. Agent Safety Constraints

### 8.1 What the Agent Can Do

- Call any tool in the registered tool set with valid arguments.
- Make multiple tool calls in a single investigation.
- Request follow-up tool calls based on previous results.
- Produce natural-language conclusions and interpretations.
- Acknowledge uncertainty and describe limitations.
- Decline to answer when the data is insufficient.
- Ask for clarification (in conversational mode) if the question is ambiguous.

### 8.2 What the Agent Cannot Do

- Generate Python, SQL, shell commands, or any executable code.
- Access columns that do not exist in the dataset.
- Modify or delete dataset rows or files.
- Access the filesystem, network, or any external service directly.
- Recall information from other users' datasets or sessions.
- Cite numbers not derived from a tool call in the current investigation.
- Call tools not present in the registry.
- Bypass the validation boundary by invoking functions directly.

### 8.3 Constraint Enforcement

| Constraint | Enforcement Mechanism |
|---|---|
| No code execution | Closed tool set; no code-execution tool registered |
| No hallucinated columns | `ToolValidator` rejects unknown column names |
| No dataset mutation | `DatasetStore` opens files read-only |
| Bounded iterations | Hard counters in `InvestigationAgent` |
| No raw data in API | `ContextBuilder` never includes DataFrame rows |
| No credential leakage | Credentials from env vars only; never logged or serialized |
| No unbounded results | `ContextBuilder` applies token cap to all tool results |

These constraints are enforced at the code level, not by the model's instruction-following alone. The model could produce a response requesting a non-existent tool; the validator would reject it.

## 9. Provider Interaction

### 9.1 Request Construction

Each provider request is constructed from the same normalized inputs. A Hugging Face request contains:

```json
{
  "model": "<HF_MODEL_ID>",
  "messages": [...],          // system + conversation history + current turn
  "tools": [...],             // full tool registry as JSON schemas
  "tool_choice": "auto",      // model decides whether to call a tool or conclude
  "temperature": 0.2,
  "max_tokens": 1024,
  "stream": false
}
```

`tool_choice` is set to `"auto"` during the investigation loop. On the final turn (when the turn limit is being approached), it is overridden to `"none"` to force the model to produce a text conclusion rather than another tool call.

### 9.2 Response Handling

`HuggingFaceProvider` and `OllamaProvider` normalize every response into `ProviderResponse`. The reasoning layer reads only `ProviderResponse` fields.

**Response classification:**

| Condition | Classification | Agent Action |
|---|---|---|
| `finish_reason == "tool_calls"` and `tool_calls` is populated | Tool call response | Parse and validate |
| `finish_reason == "stop"` and `content` is populated | Text conclusion | Compose finding |
| `finish_reason == "length"` | Truncated | Log warning; treat as partial conclusion |
| `finish_reason == "content_filter"` | Filtered | Return error finding with explanation |
| Any exception from the provider | API error | Retry with backoff; surface error if retries exhausted |

### 9.3 Failure Modes and Recovery

| Failure | Detection | Response |
|---|---|---|
| Rate limit (HTTP 429) | Status code | Exponential backoff, up to 3 retries |
| Server error (HTTP 5xx) | Status code | Exponential backoff, up to 3 retries |
| Timeout | Request timeout exceeded | Return partial finding with timeout note |
| Credit exhaustion | Error message parsing | Surface credit-exhaustion message to user; halt investigation |
| Malformed JSON in response | Parse failure | Feed error back to model and request retry (counts as a turn) |
| Model refuses tool call | Empty `tool_calls` with unexpected `stop` | Treat as text conclusion; compose finding from available evidence |

In all failure cases that cannot be recovered within the turn budget, the agent transitions to `COMPOSING` and produces a finding that explicitly notes the failure and the evidence collected up to that point.

## 10. Investigation Record and Reproducibility

At the end of each investigation, `InvestigationRecord` serializes the full investigation into a JSON object and appends it to `~/.datachef/investigations/<session_id>.ndjson`.

**Record structure:**

```json
{
  "record_id": "...",
  "session_id": "...",
  "dataset_fingerprint": "sha256:<path+mtime for files; schema+row hashes for in-memory data>",
  "question": "...",
  "trigger": "conversational",
  "tool_calls": [
    {
      "call_id": "...",
      "turn_index": 0,
      "tool_name": "compare_groups",
      "arguments": {"numeric_col": "revenue", "group_col": "region"},
      "result_summary": "Region A mean: 4200, Region B mean: 3100 ...",
      "result_data": {...},
      "execution_time_ms": 42,
      "validation_passed": true,
      "error_message": null,
      "timestamp": "..."
    }
  ],
  "finding": {
    "conclusion": "...",
    "evidence": [...],
    "interpretation": "...",
    "limitations": [...]
  },
  "model_config": {
    "model_id": "...",
    "provider": "huggingface",
    "temperature": 0.2,
    "max_tokens": 1024
  },
  "hit_limit": false,
  "turn_count": 3,
  "tool_call_count": 2,
  "created_at": "..."
}
```

**Reproducibility guarantee:** Given the same `dataset_fingerprint`, the same `tool_name`, and the same `arguments`, any user can re-run the analytical tool and obtain the same `result_data`. The record contains everything needed to verify each computed result independently of the model.

**What is not stored:** Raw dataset rows, API keys, user-identifying information, full conversation history beyond the investigation scope.

## 12. Evaluation Criteria

The agent's quality is measured against six criteria. Each maps to a testable evaluation method.

### Numerical Correctness

**Criterion:** Metrics cited in findings match the output of independently computed reference calculations.

**Method:** For a set of controlled datasets with known ground-truth values, run the agent, extract numerical claims from the finding's evidence section, and compare against reference values computed directly with Polars or SciPy.

**Acceptable threshold:** 100% match for all tool-derived results (any mismatch indicates a bug, not a tolerance issue).

### Tool Selection Accuracy

**Criterion:** The agent selects an appropriate tool for each analytical question.

**Method:** For a set of labeled test questions, each paired with the expected tool or tool sequence, measure the fraction of investigations that use an appropriate tool for the core analytical step.

**Acceptable threshold:** >= 85% on the labeled evaluation set.

### Investigation Quality

**Criterion:** Follow-up tool calls provide additional evidence that meaningfully informs the conclusion.

**Method:** Human evaluation of a sample of multi-turn investigations. Rate whether each follow-up call was justified by the preceding evidence and whether it improved the finding.

**Acceptable threshold:** >= 80% of follow-up calls rated as justified.

### Insight Validity

**Criterion:** Discovered patterns are supported by the data; false positives (reported patterns with no real statistical support) are minimized.

**Method:** Use synthetic datasets with deliberately introduced patterns and null datasets with no real patterns. Measure true positive rate and false positive rate for autonomous discovery.

**Acceptable threshold:** False positive rate <= 10% on null datasets.

### Reproducibility

**Criterion:** Tool calls recorded in investigation records reproduce the same results when re-executed.

**Method:** Automated test that re-runs every tool call in a stored record and compares output to stored result.

**Acceptable threshold:** 100% (deterministic functions should always reproduce).

### Cost and Latency

**Criterion:** Average investigation stays within cost and time budgets.

**Method:** Measure inference API token usage and wall-clock time across the evaluation set.

**Targets (initial release):**
- Median investigation: <= 5 tool calls, <= 30 s, <= 5 000 prompt tokens.
- 95th-percentile investigation: <= 10 tool calls, <= 120 s, <= 15 000 prompt tokens.

## 13. Future Agent Extensions

The current single-agent design has been deliberately kept simple to allow the core investigation workflow to be evaluated and stabilized. The following extensions are explicitly deferred to future releases:

| Extension | Description | Pre-requisite |
|---|---|---|
| Streaming investigation | Stream the agent's progress to the UI turn by turn rather than waiting for the full investigation | Async agent entry points |
| Additional local runtimes | Add direct llama.cpp or similar backends | `BaseProvider` implementation |
| Sub-agent delegation | Delegate specific investigation subtasks to specialized sub-agents | Stability of the core loop |
| Multi-dataset investigation | Compare patterns across more than one dataset | Dataset context layer extension |
| Natural-language code generation | Generate reproducible Python analysis scripts as an optional output | Sandboxed execution environment |
| Adaptive tool suggestion | Learn from investigation history which tools tend to be most useful for which question types | Investigation record analysis |
| Collaborative investigation | Multiple users investigating the same dataset simultaneously | Session store redesign |

None of these extensions require changes to the core investigation loop design. They extend the agent's capabilities by adding new entry points, new tools, or new provider implementations.
